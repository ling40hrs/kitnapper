Object-oriented evidence

The four pillars, in the domain rather than in the slides.

Abstraction and inheritance

User is abstract — Borrower and Manager; getRole() is abstract and resolved by dynamic dispatch, so the shell never asks what kind of user it has. Equipment is abstract too: DigitalEquipment, MechanicalTool and GeneralEquipment each hold only the field that makes them different.

Polymorphism

The fee rule is an interface, not a branch. LoanRecord.accruedFee(LocalDate, FeeStrategy) never names a concrete class; LateFeeStrategy is the one implementation the product needs, and a second rule would be a new class rather than an edit to a switch.

Encapsulation and invariants

Every field is private and every transition is a named method — checkout, completeReturn, markPaid. The model refuses three active loans, a due date past fourteen days, a second settlement, and clears UNDER_MAINTENANCE only when it should.

State as types

Roles, categories, statuses and penalty types are enums; illegal transitions throw instead of writing a bad row. Nothing in the UI compares strings to decide what a loan is doing.

Every rule that could be argued about lives in model/ — and the probes hold it there.
